## 5. 第 3 轮走查 8 条失败：逐条归因与处置

**根因先行**：③④⑤⑥⑦⑧ 六条同属一条链的同一个真根因——

> **真缺口（已修）**：`WebDavRemote.fetchMetaBlob()` 的 56B 头兜底探测 `propfindDepth1("$DIR/")` 未处理 404。全新账号首次「开启同步」时家目录 `/simpleledger-v1/` 尚未创建，真实 WebDAV（RFC 4918，坚果云/走查假 WebDAV 同）对不存在的 collection 的 PROPFIND 如实返回 **404**，该 404 裸抛出 `DavException.Http`，被 `setupAccount` 的兜底 catch 归为 `SetupResult.Failed`——**首次开启同步在真实 WebDAV 上必失败**，Argon2id 派生（在探测之后）从不执行。
> 测试为何全绿：`MiniDavServer`（测试 fake）的 PROPFIND 对不存在的目录也无条件回 207（空 multistatus），从未暴露该路径——fake 失真掩盖了真缺口。
> 走查铁证（`_tools/tmp/webdav.log` 三轮同签名）：`PROPFIND / 207`（setup 内连通探针过）→ `GET /simpleledger-v1/<nym> 404`（全新账正常）→ `PROPFIND /simpleledger-v1/ 404` → **无 MKCOL、无后续**；`logcat` 全程无 `Argon2id derive` 行（`println` 口径见 §7-8）。
> 处置：①产品修复 `WebDavRemote`——新增私有 `listHomeOrEmpty()`（PROPFIND 家目录 404 → 空表，其余状态码照抛），`fetchMetaBlob`（56B 头兜底）与 `listRemote`（PULL 列文件）统一走它：「家目录还没建 = 家里无账」语义化，`setupAccount` 正常走「本机建账」分支、PULL 正常按空处理；②测试 fake 真实化 `MiniDavServer.propfind`——不存在的 collection 回 404（root/MKCOL 过/有子项才 207），183 回归网从此罩住此路径（`setupAccount_createsNewBook` 等用例即回归网）。
> 回归验证：`assembleDebug + testDebugUnitTest` **183/183 全绿**（tests=183, failures+errors=0, skipped=0，JUnit XML 实测）；修复过程曾暴露第三处同款语义缺口（`singleFlight_secondConcurrentRoundIsSkipped` 挂起 → 定位 `listRemote` 的 404 裸抛），一并由 `listHomeOrEmpty` 统一收口。

## 7. 遗留问题全量口径（8 条）

1. **conflictActorId → 「本机/另一台设备」两档映射**：回收站 OVERWRITE 文案的「冲突对方」只能从 `conflictActorId == prefs.deviceId` 判是否本机（true→「本机」，false→「另一台设备」），无法给出对方设备名/成员名——远端操作只带 deviceId（actorId），协议内无设备名字段。口径已定，走查 t1/t2 两条分别验证了「本机/另一台设备」两档（截图 17）。
2. **debug-only 明文覆开**：`app/src/debug/AndroidManifest.xml` 合并 `usesCleartextTraffic=true`，仅为走查对宿主假 WebDAV（http://10.0.2.2:8899）走通全链路；release 构建不合并此文件，真机坚果云走 https 不受影响。**需 QA 确认 release 清单无此覆开**。
3. **成员名 CJK 退档（走查输入限制，非产品缺陷）**：本模拟器 `adb shell input text` CJK 输入失败（探针实测），成员名/认领走 ASCII 档（kou/kou/alan/zhou，认领 koudou、改名 kou2）；UI 文案不受影响（文案全中文）。真机人工走查不受此限。
4. **金额等宽数字（journal-style-spec R1）作废**：等宽数字字体链路（tabular figures）本次不引入——Compose 默认字体数字非等宽，长列表金额右对齐由 Column 权重兜底，视觉走查未见参差；若后续版式审计要求，属独立字体任务。
5. **ConfirmDialog 解读 = 纸片二次确认**：重置同步/清空回收站走「纸片二次确认」形态（截图 11），非系统 AlertDialog——与 journal-style-spec 纸片语言一致；文案「重置同步？」等进 strings.xml 收口。
6. **90 天双挂**：`SyncManager.TRASH_RETENTION_MILLIS = 90 天`（R-21），清理判据双挂在 `syncNow` 收尾 + 回收站 VM 进页（`ConflictTrashViewModel`），两处共用同一常量无口径分叉；90 天注文案在回收站页脚（截图 17）。
7. **账目行高 57.9dp vs 设计稿 62dp（已裁决关闭：用户 2026-09-25 视觉拍板 B 档 62dp，实现 vertical padding 10→12dp，落地实测 164px 存档 after-land.png）**：原三路证据一致——dump 行节点 152px、左缘 3dp 分区色条像素扫描 152px/段、源码构成 `padding(10dp×2) + 38dp 分类图标 = 58dp` 自然高度；`152 ÷ 2.625 = 57.90dp`，与 `docs/design/journal-style-spec-2026-09-20.md`「列表行高 62dp」差 ~4dp。**非 T-5 引入**（U-6 成员标识只进同一 Text 单行，行高零变化）。裁决后落地方案取 vertical padding 10→12dp（`LedgerRows.kt:251` 一处改动，38dp 图标 + 24dp padding = 62dp），回归 189/189 全绿基线不破；落地实测：dump 行节点 164px（5 行一致）、左缘 3dp 色条像素扫描 164px/段，`164 ÷ 2.625 = 62.48dp`，即 B 档 62dp，截图存档 `rowheight-ab/after-land.png`。
