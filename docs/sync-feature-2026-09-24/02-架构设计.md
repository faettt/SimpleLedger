## 0. 一句话架构

每台设备持有**本地操作日志（op-log）**：一切增删改在同一事务里追加为不可变操作（observed-remove CRDT），云端只是**追加式加密操作分片 + 内容寻址照片**的中转盘（用户自己的 WebDAV，Argon2id→AES-256-GCM 端到端密文，文件名为 HMAC 假名/随机名）；每轮同步 = 推自己的分片 + 拉别人的分片 + 幂等回放合并 + 照片按 hash 补传——**永不丢账**由「操作全集的纯函数重放 + 删/改双留进冲突回收站」保证。

## 1. 实现方案 + 框架选型（含 V1–V4 验证结论与证据）

### 1.1 核心技术难点

| # | 难点 | 对应需求 | 解法概要 |
|---|---|---|---|
| H1 | 本地自增 Long 主键跨设备必冲突；引用关系（entry→category/section/image）如何跨设备保持 | R-11 | 每表增列全局 `syncId`（32hex 随机 UUID 变体），**本地 Long 仅作本地键**；一切跨设备引用在操作载荷里以 syncId 表达，应用时映射回本地 Long；存量迁移生成 syncId 并保持本地引用不动 |
| H2 | 乱序/重复/断点投递下收敛一致、永不丢账；删/改冲突双留 | R-07/R-08 | 操作级 CRDT：UPSERT 全量快照 + **观察者删除（observed-remove）** DELETE（携带 baseSeq）；合并是操作全集的纯函数，天然幂等收敛（见 §3.5） |
| H3 | 网盘只见密文，含文件名；同口令设备互通、口令错可判 | R-04/R-05 | Argon2id→主密钥→HKDF 子密钥（encKey/nameKey）；AES-256-GCM 加密一切内容；文件名=HMAC 假名或随机名；密文头存盐/参数/KCV（见 §1.6） |
| H4 | 照片不重传、不重复占空间、默认不吃流量 | R-16/R-17 | 照片明文 SHA-256 内容寻址 → 云端文件名 = HMAC(nameKey, hash) 确定性假名；上传前 HEAD 探存在；仅 Wi-Fi 门控在引擎照片阶段 |
| H5 | 合并顺序安全（RESTRICT 外键）、事务可回滚 | R-12 | 同轮操作按 `SECTION→CATEGORY→ENTRY→IMAGE→MEMBER→SETTING` 分层 + 层内按 (seq, actorId, opId) 排序，**单事务**应用，任一失败整体回滚重试；引用未到的操作挂起（applied=0）下轮重试 |
| H6 | 后台兜底 + 启动/回前台触发，失败不打扰 | R-13/R-14 | WorkManager 周期 30 分钟 + `MainActivity.onCreate` / `ProcessLifecycleOwner.ON_START` 双挂接；SyncState 状态机 StateFlow 供角标，失败静默 |
| H7 | 新设备接入只合并不选方向；种子数据不撞车 | R-15 | 双向合并=操作并集；**初始分区/分类使用确定性 syncId**（由种子 key 派生），两台设备的默认数据天然是同一逻辑行，不会合并出双份（见 §3.6） |

### 1.3 V1 实测：Argon2id 在 Android（minSdk 26）的可用库

**结论：选 `org.bouncycastle:bcprov-jdk18on:1.86`，纯 Java 直调 `Argon2BytesGenerator`。**

证据（全部本机实测，2026-09-24）：

1. **Maven 坐标与版本**：`repo1.maven.org/maven2/org/bouncycastle/bcprov-jdk18on/maven-metadata.xml` 实查，最新 `1.86`（metadata 更新至 2026-09-11）。
2. **字节码兼容**：`javap -verbose` 实测 `org.bouncycastle.crypto.generators.Argon2BytesGenerator` → **major version 52（Java 8）**，minSdk 26 直接可跑，无 desugar 需求。
3. **正确性（关键）**：JVM 试运行（`/tmp/sl-verify/Verify.java`，编译运行均过）对 **RFC 9106 §5.3 Argon2id 官方测试向量**（P=0x01×32, S=0x02×16, K=0x03×8, X=0x04×12, v=0x13, m=32KiB, t=3, p=4, T=32）输出：
   `0d640df58d78766c08c037a34a8b53c9d01ef0452d75b65eb52520e96b01e659` —— 与 RFC 期望值**逐字节一致 → PASS**。
4. **Android 工具链实证**：在本工程临时引入该依赖 + 引用类（`SyncSmoke.kt`，验证后已删除回滚），执行 `JAVA_HOME=~/Library/Java/JavaVirtualMachines/temurin-17/Contents/Home gradlew -p <repo> :app:assembleDebug` → **BUILD SUCCESSFUL in 54s**，`dexBuilderDebug`/`mergeProjectDexDebug` 均执行（即 dex 打包通过）。
5. **无桌面依赖**：对 Argon2 调用链 9 个类（Argon2BytesGenerator / Argon2Parameters / Pack / Strings / Arrays / HMac / SHA256Digest 等）逐类扫描常量池，**无 `java/awt`、`java/desktop`、`javax/swing` 引用 → 纯 Java**。

**关键 API 签名（javap 实测）**：

```kotlin
// org.bouncycastle.crypto.generators.Argon2BytesGenerator
fun init(params: Argon2Parameters)
fun generateBytes(password: CharArray, out: ByteArray): Int
fun generateBytes(password: CharArray, out: ByteArray, outOff: Int, len: Int): Int
fun generateBytes(password: ByteArray, out: ByteArray): Int

// org.bouncycastle.crypto.params.Argon2Parameters.Builder
Argon2Parameters.Builder(type: Int)              // ARGON2_id = 2
    .withVersion(Argon2Parameters.ARGON2_VERSION_13)  // 0x13
    .withMemoryAsKB(kb: Int).withIterations(t: Int).withParallelism(p: Int)
    .withSalt(salt: ByteArray).withSecret(secret: ByteArray).withAdditional(ad: ByteArray)
    .build()
```

**用法约束**：只 new 类直调，**不** `Security.addProvider(BouncyCastleProvider)` —— 避开 Android 系统内置旧版 BC Provider 的类冲突（Android 官方已知坑）；R8 会裁掉未用的 5800+ 类，release 体积可控。

**落选方案实测依据**：

| 候选 | 坐标（实查） | 落选理由 |
|---|---|---|
| argon2-jvm | `de.mkammerer:argon2-jvm:2.12` | POM 实查：→ `argon2-jvm-nolibs:2.12` → **`net.java.dev.jna:jna:5.16.0`**（JNA 在 Android 上需额外 native 适配、体积大、稳定性差）；JNI 装载在 16KB page size 新机型风险未覆盖 |
| lazysodium-java | `com.goterl:lazysodium-java:5.2.0` | POM 实查：→ `jna:5.17.0` + `resource-loader` + `slf4j-api`；Android 需换 `lazysodium-android:5.2.0`（原生 .so 按 ABI 打包），为一个 KDF 引入整套 libsodium 无必要 |
| password4j | `com.password4j:password4j:1.8.4` | Argon2 走自带 JNI（jar 内解压装载 .so）；Android ABI/16KB page 兼容未实测覆盖，装载失败是运行期风险；bcprov 已全绿 |

**派生参数定案**：`m=65536 KiB（64 MiB），t=2，p=1，salt=16B 随机，输出 32B`。参数随密文头存储（可调参不破兼容）；低端机耗时以真机实测为准（见 §8 待明确 U-1）。

### 1.4 V2 实测：WebDAV 客户端方案

**结论：自研最小 WebDAV 客户端（OkHttp 5.5.0），不用 Sardine。**

证据：

1. **Sardine 主线 `com.github.lookfirst:sardine:5.13`**（Maven Central 最新版，2025-01）POM 实查依赖：
   - `org.apache.httpcomponents:httpclient:4.5.14` —— Apache HttpClient 4.x 自 API 23 起被 Android 移出 SDK（除非 useLibrary 老库），在现代 Android 上是历史包袱；
   - `jakarta.xml.bind-api:4.0.2` + `org.glassfish.jaxb:jaxb-runtime:4.0.5` —— JAXB 运行时在 Android 上不可直接用（缺 SE 模块体系），需自行裁剪移植；
   - 编译目标 Java 11，且其 `put` 对 **If-Match / If-None-Match 条件写**无一等 API，断点续传/流式边加解密边传更无从谈起。
   → **Android 兼容成本高、关键需求（条件请求）不满足，否决。**
2. **Android 分支 `com.thegrizzlylabs:sardine-android`**：`repo1.maven.org` 对应路径 **无 maven-metadata（404）**，jcenter 已关停 → 无法经 Maven Central 解析，违反「能引 Maven 依赖即可」的前提，否决。
3. **OkHttp `com.squareup.okhttp3:okhttp:5.5.0`**（Central 最新版，2026-08）：与 bcprov/WorkManager 一同参与本工程 `:app:assembleDebug` 实测 **BUILD SUCCESSFUL + dex 通过**；零历史包袱；`Request.Builder` 天然支持任意方法（PROPFIND/MKCOL）与任意头（If-Match/If-None-Match/Range/Depth），流式 body 直接对接加解密管道。

**需求覆盖对照（自研客户端 `MiniWebDavClient`）**：目录创建=MKCOL（405/301 视为已存在）；文件 PUT/GET=流式 RequestBody/ResponseBody；PROPFIND（`Depth: 1`，XmlPullParser 解析 `d:href/d:getcontentlength/d:getetag/resourcetype`，不引 JAXB）；条件请求=头级支持（照片去重写用 `If-None-Match: *`，meta 首写用 `If-None-Match: *`，后续任何覆盖写用 `If-Match: etag`）；弱网续传=GET `Range`（R-23）。

### 1.5 V3 实测：WorkManager 约束与触发挂接点

**结论：周期兜底 = 30 分钟（拍板值，≥15 分钟下限），`NetworkType.CONNECTED` 约束；四路触发挂接。**

证据：

1. **15 分钟下限确认（字节码级）**：下载 `androidx.work:work-runtime:2.12.0.aar`（Google Maven 最新为 2.12.0）并解包 `classes.jar`：
   - `androidx/work/PeriodicWorkRequest$Companion.class` 常量池含字段名 **`MIN_PERIODIC_INTERVAL_MILLIS` / `MIN_PERIODIC_FLEX_MILLIS`**（javap/字符串扫描实测）；
   - `androidx/work/impl/model/WorkSpec.class` 字节码含 **`900000`**（= 15×60×1000 ms）钳制字面量（Python 扫描 class 字节实测）。
   → 「周期任务最短 15 分钟」确认成立，PRD Q-2 的口径无冲突；30 分钟兜底合法且更省电。
2. **Doze 口径**（验收口径按 PRD R-13 原文「受系统 Doze 约束，尽力而为」）：周期任务受 Doze / App Standby / 厂商杀后台影响，**不承诺准时触发**；正确性不依赖它（启动/回前台/手动都会同步，操作日志保证漏一轮无损）。
3. **启动/回前台挂接点（读码确认）**：
   - **冷启动**：`MainActivity.onCreate`（全 App 唯一 Activity，`FragmentActivity`）→ 经 `LedgerApp.container` 取 `SyncManager.requestSync(COLD_START)`；
   - **回前台**：项目已引入 `androidx.lifecycle:lifecycle-process` 且 `ui/security/AppLock.kt` 已示范标准挂法（`ProcessLifecycleOwner` + `DefaultLifecycleObserver`，ON_START/ON_STOP 记时）——同步复用同一挂法，`ON_START` 触发 `requestSync(FOREGROUND)`，**去抖**：距上次成功同步 < 60s 跳过（避免切屏抖动反复同步）；
   - **手动**：U-1「立即同步」按钮；
   - **后台兜底**：`SyncWorker`（`CoroutineWorker`）→ `syncOnce(PERIODIC)`；`enqueueUniquePeriodicWork("simpleledger-sync", ExistingPeriodicWorkPolicy.KEEP, 30min)`。

### 1.6 V4 实测：AES-GCM 与文件名确定性方案

**结论：内容 = AES-256-GCM（javax.crypto，随机 12B IV）；文件名 = HMAC-SHA256 确定性假名（内容寻址）/ 随机名（操作分片）——不引 Tink，不用固定 IV。**

证据：

1. **AES-GCM 可用性**：`Cipher.getInstance("AES/GCM/NoPadding")` + `GCMParameterSpec(128, iv)` JVM 试运行：加解密 roundtrip **PASS**、单字节篡改解密**被拒 PASS**；同 API 参与 `:app:assembleDebug` 实测编译 dex 通过。Android 侧该组合自 API 19（Conscrypt）稳定可用，minSdk 26 无虞。
2. **HKDF-SHA256**（子密钥派生）：手写 RFC 5869 实现对官方**附录 A.1 测试向量**输出 `3cb25f25faacd57a90434f64d0362f2a…5865` 逐字节一致 **PASS**。
3. **HMAC 确定性文件名**：同一 canonical 输入两次派生**同名**、不同输入**异名** 实测 **PASS**（`base32lower(HMAC-SHA256(nameKey, "v1:"+kind+":"+canonical))` 截 26 字符）。

**文件名方案取舍（确定性加密才能让同名映射稳定）**：

| 方案 | 评估 | 结论 |
|---|---|---|
| AES-SIV（Tink `DeterministicAead`/AES256_SIV） | `com.google.crypto.tink:tink-android:1.23.0` 存在可行，但为「可逆的文件名加密」引入 2MB+ 依赖；而云端文件**从不需要反解出原名**（映射由内容 hash / 分片序号在本地推导） | 能力过剩，弃 |
| AES-GCM + 固定 IV | 固定 IV 违背 GCM 安全前提（同密钥 IV 复用即灾难性泄钥） | 密码学禁忌，弃 |
| AES-GCM + 合成 IV（HMAC 派生 IV） | 可行，但本质是「PRF + GCM」的复杂化写法，收益为零 | 过度设计，弃 |
| **HMAC-SHA256 假名（选定）** | PRF 性质：同输入稳定同名（R-16 内容寻址去重的必要条件）、异输入不可关联、不可逆；nameKey 与 encKey 经 HKDF 分域派生；实现 20 行、零新依赖 | **选定** |

R-04「云端文件名全加密」以 PRD 原文口径「云端目录仅见密文与**随机/密文命名**」满足：
- **照片**：`photoName = nym(nameKey, "photo:" + sha256hex(明文JPEG))` —— 确定性假名（跨设备同照片同名 → 去重/免传）；
- **操作分片**：`chunkName = 128bit SecureRandom hex + ".op"` —— 随机名（每设备写自己的分片，零写冲突，无需确定性）；
- **元文件**：`metaName = nym(nameKey, "meta")` —— 确定性假名（各设备算出同一入口）。

**密钥派生链**（全部原语实测）：

```
password ──Argon2id(salt, m=64MiB, t=2, p=1)──► masterKey(32B)
masterKey ──HKDF-SHA256(info="SimpleLedger/v1/enc")──► encKey(32B)   // 内容 AES-256-GCM
masterKey ──HKDF-SHA256(info="SimpleLedger/v1/name")──► nameKey(32B) // 文件名 HMAC
kcv = HMAC-SHA256(encKey, "SimpleLedger/v1/check")[0..16)            // 口令校验值
```

口令错判据（R-04「口令不一致」）：从云端 meta 头取 salt/参数 → 派生 → 比对 KCV，不等即报「口令不一致」，**在下载任何数据前失败**。KCV 是标准 key-check-value，不泄露口令信息。口令忘 = 云端作废本地无损（R-05「重置同步」= 删云端布局 + 新盐新口令重建，本地数据零触碰）。

### 1.7 同步引擎与 CRDT 模型概要（细节见 §3）

- **同步身份**：4 表增 `syncId`（32hex）+ `versionSeq`（行级因果计数）；`entries` 增 `memberId`；本地 Long 主键保持现状。
- **操作日志** `sync_ops`：UPSERT（全量快照）/ DELETE（带 `baseSeq` 的观察者删除，快照进回收站）；opId 幂等。
- **合并语义（observed-remove，纯函数收敛）**：一条 UPSERT 被某 DELETE「观察过」（`delete.baseSeq ≥ upsert.seq`）才死；否则存活。⇒ 删∥改必双留（改动版活、被删旧版进 `sync_trash`）；纯删除也留底。同 seq 冲突（同基数并发编辑）按 (seq, actorId) 全序 LWW，确定性收敛。
- **云端布局**（坚果云/任意 WebDAV，全部密文）：

```
<dav-root>/simpleledger-v1/
    <nym(meta)>            # 元文件：明文头(KDF参数/salt/KCV) + 密文体(bookId 等)
    <random>.op …          # 操作分片（每设备自写、追加式、If-None-Match:*）
    <nym(photo:hash)> …    # 照片（内容寻址，If-None-Match:* 防重复）
```

- **一轮同步**：PUSH（outbox→分片→PUT）→ PULL（PROPFIND 差集→GET→解密→幂等回放）→ PHOTOS（hash 差集上下行，Wi-Fi 门控）→ 状态收尾。
- **设置**：6 项字段级 LWW（R-06）；照片 Wi-Fi 开关是**设备本地**偏好，不参与同步。
- **首次接入**：测连接→读/建 meta→KCV 验口令→认领成员→存量全量导出为操作→常规同步（并集，无「覆盖方向」，R-15）。

### 1.8 与现状的兼容口径

- Room **v4→v5 迁移保数据**（只 ALTER ADD + CREATE TABLE + 补 UPDATE，不重建表，不撞 RESTRICT——外键运行期本就关闭，见 AppDatabase 守卫注释）；`MigrationSqlTest` 钉死语句与顺序。
- 本地 4 秒撤销（`deleteEntryWithSnapshot` + `cache/parked_images`）**保持不动**；与冲突回收站分层并存（撤销窗口 = 体验层，回收站 = 持久层）。
- 金额 Long「分」、语义色禁 `isSystemInDarkTheme`、颜色只表分区身份、动效唯一源 `ui/theme/Motion.kt` —— 全部沿用（见 §7）。

迁移口径（验收 R-11「迁移前后逐笔无损」）：全部是 ADD COLUMN / UPDATE / CREATE INDEX，**零 DROP、零重建表**；entries→categories/sections 的引用是本地 Long id，原值不动 ⇒ 引用关系保持。`contentHash` 存量为空串，由 `LedgerApp` 启动后台一次性补算（读文件→sha256→改名 `<hash>.jpg`→回填），补算完成前照片不参与同步（只同步账目，不丢）。

### 3.4 操作模型（`op/SyncOp.kt`）

```kotlin
enum class RowKind { SECTION, CATEGORY, ENTRY, IMAGE, MEMBER, SETTING, TRASH }
enum class OpType { UPSERT, DELETE, TRASH_ACT }

/** 行级因果版本：seq=行 Lamport 计数，actorId=打破平局（时钟偏移免疫） */
data class RowVersion(val seq: Long, val actorId: String) : Comparable<RowVersion> {
    override fun compareTo(other: RowVersion): Int =
        compareValuesBy(this, other, { it.seq }, { it.actorId })
}

data class SyncOp(
    val opId: String,                 // UUID.randomUUID()
    val rowKind: RowKind,
    val rowSyncId: String,
    val opType: OpType,
    val actorId: String,              // SyncPrefs.deviceId
    val memberId: String?,            // 操作人（SyncPrefs.selfMemberId）
    val seq: Long,                    // UPSERT：parent.versionSeq + 1；DELETE/TRASH_ACT：DELETE 传 0
    val baseSeq: Long?,               // UPSERT：编辑时观察到的行 versionSeq（新建=null）；DELETE：被删行当时的 versionSeq
    val payload: JSONObject,          // 见 §3.7 载荷快照
    val createdAt: Long,
)
```

**payload 快照字段（UPSERT）**：
- SECTION：`{name, iconId, note, budgetCents, colorIndex, sortOrder, createdAt}`
- CATEGORY：`{name, iconId, type, sectionSyncId?, sortOrder}`（**严禁 0L 表示全局**，全局=null 落 JSON 为缺省）
- ENTRY：`{type, amountCents, categorySyncId, sectionSyncId, entryTime, note, reconciled, reimburseState, createdAt, updatedAt, memberSyncId?}`
- IMAGE：`{entrySyncId, contentHash, sortOrder}`
- MEMBER：`{name, hidden, createdAt}`
- SETTING：`{key, value}`（key ∈ AppSettings 六项）
- TRASH_ACT：`{action: "RESTORE" | "PURGE"}`

DELETE payload = 删除方观察到的行快照（同 UPSERT 字段）+ `_deletedAt`（回收站展示用）。

### 3.5 CRDT 合并规则（`OpApplier`，收敛性契约 —— 实现与单测的唯一依据）

对每个 (rowKind, rowSyncId) 的操作全集 **O**（按 opId 幂等去重后）：

1. **存活判定（observed-remove）**：
   `U_live = { u ∈ O | u.opType=UPSERT ∧ ¬∃ d ∈ O: d.opType=DELETE ∧ d.baseSeq ≥ u.seq }`
   即：一条更新只有在**被某次删除观察过**（删除方的 baseSeq ≥ 它的 seq）时才死；并发/更晚的更新杀不死。
2. **行状态**：`U_live ≠ ∅` ⇔ 行存活；状态 = `max(U_live)` 按 `RowVersion(seq, actorId)` 全序（LWW，同 seq 平局按 actorId 字典序，确定性）。
3. **回收站推导**：每个 DELETE 操作 d ⇒ upsert `sync_trash(deleteOpId=d.opId, snapshot=d.payload, deletedAt, deletedByMemberId)`；`conflict = (U_live ≠ ∅)`，`conflictActorId = argmax(U_live).actorId`。
   - 删∥改：d.baseSeq=1，改 u.seq=2 > 1 → u 存活 ⇒ **改动版在账、被删旧版进回收站**（R-08 双留）✓
   - 纯删除：d 观察了唯一更新（baseSeq ≥ 其 seq）⇒ 行死 + 回收站留底 ✓
   - 双删：两个 DELETE 各留一条回收站记录（resolved 独立推进），行死 ✓
4. **TRASH_ACT**：`{RESTORE|PURGE}` 作用于 `rowSyncId = 目标 deleteOpId` 的回收站条目：RESTORE = 同事务内「以**原 syncId**、`seq = max(seq)+1` 插回 UPSERT」+ 条目标记 resolved=1；PURGE = resolved=2。
5. **应用顺序与事务**：同一轮全部远端操作在**一个 Room 事务**内应用；先按 `SECTION→CATEGORY→ENTRY→IMAGE→MEMBER→SETTING→TRASH` 分层（尊重 RESTRICT 引用序，R-12），层内按 `(seq, actorId, opId)` 排序；应用后重算受影响行投影。事务抛错 → 整体回滚，标记本轮失败，下轮重试（幂等，重放无副作用）。
6. **引用判定（三分——实现细化追认，收敛性关键）**：操作引用的 syncId（categorySyncId/sectionSyncId/entrySyncId/memberSyncId）按三档判定：
   ① 引用解析到行 → 正常应用；
   ② 行不在、但**操作全集认识它**（创建/更新操作到过且已死）→ **占位落库**（ENTRY 挂 0 走「未分类」、CATEGORY 的 sectionSyncId 占位降级全局，同 `detachFromSection` 语义）；
   ③ 操作全集**也不认识** → 真挂起（`applied=0` deferred），每轮应用末尾 + 下轮开始时重试挂起集，上限告警阈值 50（防永久孤儿——理论上创建先于引用，仅网络撕裂窗口出现）。
   理由：二分口径（挂起/应用）下「删∥增引用」两机会产生分歧投影（一边有行、一边永久挂起），违背 §3.5-7 纯函数收敛。单测 `OpMergeTest.r08DeleteVsCreateReferenceNeverLosesData` + `deferredUntilReferenceArrivesThenRetryApplies` 钉死。
7. **收敛性**：以上规则是操作全集的纯函数；操作集合并满足交换/结合/幂等 ⇒ 任意投递顺序/重复收敛一致（R-07）。单测 `OpMergeTest` 对「A 增 3 删 1 改 1 ∥ B 增 2 改 2」及乱序/重复矩阵逐项断言。
8. **并发编辑双留（U-3 已裁定，D5「永不丢」延伸到编辑历史）**：
   1. UPSERT 操作**也携带 `baseSeq`**（= 编辑时观察到的行 `versionSeq`；新建行为 null）。串行覆盖判定：`u_j` 串行覆盖 `u_lo` ⇔ `u_j.baseSeq ≥ u_lo.seq`；否则若 `u_j.baseSeq < u_lo.seq` 且 `u_lo.baseSeq < u_j.seq`，则二者**并发**（互不观察）。
   2. 回收站推导补一条：`U_live` 中存在**并发且 LWW 落败**的版本 `u_lo`（∃u_j ∈ U_live：`RowVersion(u_j) > RowVersion(u_lo)` 且二者互不观察）⇒ `u_lo` 进 `sync_trash`：主键 `deleteOpId = u_lo.opId`（稳定幂等键），`conflict = 1`，`conflictActorId = argmax` 方 `actorId`，`source = 'OVERWRITE'`（来源语义「被修改覆盖」，区别于删除类留底）。
   3. **串行覆盖的历史版本不留底**（防止回收站被编辑历史刷屏）。
   4. 对该类留底条目做 `TRASH_ACT(RESTORE)`：以**原 syncId**、`seq = 当前 max(seq)+1`、`baseSeq = 当前 max 版本的 seq`（串行）插回 UPSERT —— 即用户主动回滚，**被覆盖的现版本不留底**；`PURGE` 同现有语义。
   5. `sync_trash.source` 区分 `'DELETE'`（删除留底，含删∥改的被删旧版）与 `'OVERWRITE'`（覆盖留底）；两类条目在 UI 的文案区分由 T-5 定稿。

### 3.8 Repository 埋点契约（`LedgerRepository` 改造要点）

- 构造签名：`LedgerRepository(db, imageStorage, ops: OpRecorder)`。
- **每个写方法**的表写 + `ops.onXxx` 必须在**同一个** `db.withTransaction {}` 内（失败同回滚，R-12）：`saveSection/saveCategory/saveEntry/deleteSection/deleteCategory/deleteEntry(WithSnapshot)/restoreEntry/setEntryReconciled/setEntryReimburseState/reorderSections/reorderCategories`。
- 新行首次入库时生成 `syncId = UUID.randomUUID().hex32`、`versionSeq = 1`；更新时 `versionSeq = old + 1`、`updatedAt = now`；UPSERT 操作的 `baseSeq` = 编辑时观察到的 `versionSeq`（新建 null，§3.5-8）。
- `deleteEntryWithSnapshot`：快照**增含 syncId/versionSeq/images(contentHash+syncId)/memberId**，并同事务 `ops.onDelete(ENTRY, syncId, baseSeq, snapshot)`（→ 回收站推导，R-08 纯删除也留底）。
- `restoreEntry`（4 秒撤销）：**复用原 syncId**（`seq = baseSeq+1`，天然不被已记的 DELETE 杀死）+ `ops.onTrashAct(deleteOpId, PURGE)` 把刚产生的留底撤下；若删除操作尚未上传（`uploaded=0`），撤销可直接**连操作一起摘除**（更干净，首选路径）。
- `ImageStorage`：`promoteToStorage` 改为 `filesDir/images/<sha256(字节)>.jpg`；删除文件前查 `contentHash` 引用计数（>1 不删文件，防共享照片误删）。

## 4. 程序调用流程（时序图）

> 完整 Mermaid 源码见同目录 `sequence-diagram.mermaid`（一轮同步）、`sequence-diagram-setup.mermaid`（首次接入）、`sequence-diagram-conflict.mermaid`（删改冲突合并）。此处为文字版要点。

### 4.1 一轮同步（自动/手动同路径）

```
Trigger(启动/回前台/Worker/按钮) → SyncManager.requestSync（去抖+单飞）
  → SyncEngine.syncOnce:
    [PUSH_OPS]  SyncDao.outbox() → 分片(≤128 条或 ≤256KB)
                → gzip → SyncCrypto.seal → WebDavRemote.uploadChunk(If-None-Match:*)
                → SyncDao.markUploaded(opIds, chunkName) + 台账 sync_remote_files
    [PULL_OPS]  WebDavRemote.listRemote() ⊖ sync_remote_files → 新分片 GET → open → OpCodec.decode
    [MERGE]     OpApplier.applyRemote(单事务, §3.5 规则) → 行投影 + 回收站推导 + 挂起重试
    [PHOTOS]    PhotoTransfer.syncPendingPhotos()（Wi-Fi/额度门控；上行 HEAD 去重→PUT；下行 GET→hash 校验→落盘）
    → state = Idle；记 lastSyncAt
  失败任一步 → state = Failed(reason)（静默，仅角标）；下次触发重试（outbox/台账天然断点）
```

### 4.2 首次接入（新设备，R-15）

```
UI 同步设置页（U-1）→ 填 WebDAV 凭证 → SyncManager.testConnection（PROPFIND 根；401→凭证错 / 超时→网络错）
  → 设置同步口令 → WebDavRemote.readMeta?
       有 meta：从明文头取 salt/参数 → deriveKeys → KCV 不符 → 「口令不一致」终止（R-04）
       无 meta：writeMetaOnce(If-None-Match:*)（竞争 412 → 重读 meta 走「有 meta」路径）
  → 成员认领（U-2：全书唯一名，冲突换名；生成 member UUID）
  → 存量导出：全部 sections/categories/entries/entry_images 按 §3.7 快照生成 UPSERT 操作（upserted=LOCAL outbox）
  → 同步一轮（§4.1）——双向合并取并集，全程无「覆盖方向」提示
```

### 4.3 删/改冲突合并（S2 定向用例）

```
A 机删除账目 X：op d(opId=D, DELETE, baseSeq=1, payload=旧版快照)     [A 本地：X 删除 + 回收站(纯删)]
B 机修改账目 X：op u(opId=U, UPSERT, seq=2, payload=改动版快照)        [B 本地：X = 改动版]
两机各自上传分片 → 任一机下轮拉到对方操作 → OpApplier.applyRemote:
  X 的操作集 = {u, d}：d.baseSeq=1 ≥ u.seq=2? 否 → u 存活 ⇒ X = 改动版（正常在账）
  d 产生回收站条目：conflict=1（X 存活），conflictActorId=B.actor ⇒ 「被 A 删除，被 B 修改」
  ⇒ S2：改动版正常存在，被删旧版可在「冲突回收站」查看/恢复/彻底删除 ✓
恢复 = TRASH_ACT(RESTORE)：以原 syncId、seq=3 插回（若 X 已存活则 RESTORE 退化为 no-op + 条目消解，UI 提示「该账目已有新版本」）
```

## 7. 共享知识（跨文件约定）

1. **金额/时间**：金额一律 `Long`「分」；时间一律 epoch millis（UTC 瞬时），展示走 `DateTimes`。语义色禁 `isSystemInDarkTheme`；颜色只表分区身份（R3）——同步状态**不得新增颜色语义**，只用图标形态 + 文案。
2. **动效**：只引用 `ui/theme/Motion.kt` 的 `SlMotion` 档位/曲线（同步中=旋转墨点遵循 Motion 缓动；角标切换用 `slFast`）；禁止散写时长/曲线。
3. **同步身份**：跨设备引用**只用 syncId**（32hex 小写）；本地 Long id 永不出现在操作载荷。全局分类的归属 = JSON 缺省/null，**严禁 0L**。
4. **加密文件格式 v1**（一切云端 blob 通用，`CryptoFormat`）：

```
偏移   长度   内容
0      4     MAGIC "SLC1"（明文）
4      1     purpose（0=ops, 1=photo, 2=meta）
5      1     formatVersion = 1
6      4     kdf.mKiB (u32 BE)
10     1     kdf.t
11     1     kdf.p
12     16    kdf.salt
28     12    GCM IV（随机）
40     16    kcv（仅 purpose=meta 非空，其余全 0）
56     n     AES-256-GCM 密文（明文体先 gzip；tag 16B 附密文尾）
```
头（56B）**明文**——盐/参数/KCV 无泄露问题（PRD 认可）；版本不符→`SyncError.CORRUPTED`。meta 明文体 = `{bookId, createdAt}`；kcv 比对失败→「口令不一致」。

5. **同步协议**：目录 `simpleledger-v1`（协议版本号=1，破坏性升级换目录并存）；操作分片上限 128 条或 256KB；操作 JSON 字段名稳定不复用（改字段=加新字段+弃旧字段）。
6. **文件命名**：照片 `nym("photo:"+sha256hex)`、meta `nym("meta")`（假名=小写 base32 截 26 字符）；操作分片=随机 32hex+".op"。**云端永不出现任何明文名**（S4）。
7. **错误处理口径**：同步失败**一律静默**（零弹窗，S6/R-13/R-14）→ `SyncError` 枚举 → UI 层映射中文文案（「口令不一致」「网络不可用」「凭证无效」「云盘空间/流量不足」「数据已损坏」）；数据层只抛/归类，不写死文案；文案全进 `strings.xml`。
8. **CRDT 契约**：§3.5 八条是实现与单测的唯一依据；`OpApplier` 保持纯函数式（输入操作集→输出状态），禁止在合并路径读系统时间/做网络。
9. **事务契约**：`OpRecorder` 调用必须与业务写同在 `db.withTransaction`；文件 IO（照片移动/删除）一律在事务**外**先/后置（沿用 `saveEntry` 现行三段式）。
10. **凭证与口令存储**：WebDAV 凭证 + KDF 参数/KCV 存应用私有 SharedPreferences（明文）——R-01「仅存本地、不上传」；不引 `security-crypto`（官方已废弃）；root 级威胁不在本 PRD 范围（口令保护的是云端，本地备份安全另论）。
11. **成员**：全员全权（D7，不做只读）；成员**可隐藏不可删**（拍板）；成员名全书唯一（并发撞名双留 + UI 提示改名）。
12. **构建命令**：`JAVA_HOME=~/Library/Java/JavaVirtualMachines/temurin-17/Contents/Home gradlew -p /绝对路径 :app:assembleDebug`（禁 `cd &&` 前缀）。
