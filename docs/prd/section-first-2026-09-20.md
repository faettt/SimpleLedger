## 1. 背景与问题

### 1.1 用户是谁

单一用户：一位**正在装修的业主**。核心心智模型是「**装修这件事有 26 万预算，我要盯着它**」。记账对 TA 不是记流水，而是**盯住几个花钱的"桶"**。

### 1.2 现状（已实际读代码确认，含证据位置）

| 现状事实 | 代码位置 |

### 1.3 用户的原始三点不满（原话）与对应的真实痛点

**不满 1：「记一笔」的记账逻辑我不喜欢，我希望是软件内分区管理，选定某个分区后就在那个分区内添加记账，而不是每次要重新选择分区。**

> 痛点场景：用户在建材市场买瓷砖，打开 App = 明细页 → 点中央 ＋ → 表单 → 滚到中间那一行分区 chips → 在「日常开支 / 装修 / 旅行」里挑「装修」→ 再往上滚回分类选「购物」→ 填金额。
> 「装修」这一行**每次都要重选一次**，而且它默认停在「日常开支」——手一滑就记错桶，且错得毫无提示。**分区是用户真正的第一决策，却被降级成了表单里一个默认错、要重选的中间步骤。**

**不满 2：分区和分类的搭配逻辑不完善：不管选择什么分区，都是相同的分类选择。**

> 痛点场景：装修分区里出现的是「餐饮 / 交通 / 购物 / 医疗 / 娱乐 / 学习」这套通用分类。用户真正想按「主材 / 人工 / 家具 / 家电 / 设计费」拆装修的钱，但**分类体系是全局的、扁平的**，既不能按分区区分，也无法让「装修」拥有自己那套分类。结果：26 万预算的进度条有了，**钱花在哪个环节却看不出来**——而这恰恰是装修业主最想知道的。

**不满 3：UI 展示能再简单明了，减少阅读压力。**

> 痛点场景：一屏之内要面对：月份头 + 三格概览（支出/收入/结余）+ 分区筛选 chips + 可能的活动筛选条 + 按天分组的账目 + 底部 5 槽（含凸起按钮）；进表单又是一屏 8 个区块。信息平铺、层级不分明，**用户每做一件事都要先"找"**。

## 2. 设计目标

### 2.1 本次要达到什么

| # | 目标 | 判定口径（一句话） |
|---|---|---|
| G1 | **分区成为第一入口与记账上下文** | 打开 App 第一屏即分区；任何一笔账都天然属于某个分区，不需要在表单里再选一次 |
| G2 | **分类拥有归属层级** | 分类分「全局」与「分区专属」，选中某分区时，可选分类 = 匹配类型的全局分类 + 该分区的专属分类 |
| G3 | **降低阅读压力** | 减少一屏内的并列信息块：导航 5→4 槽；表单去掉「分区」行；分区详情只承载"这个分区的账" |

### 2.2 明确不做什么（Out of Scope）

| # | 不做 | 依据 |
|---|---|---|
| N1 | **不做**分类的自动常用度 / 使用频次排序 | D3（用户明确要求手动排序） |
| N2 | **不做**独立收入入口 | D9（收入也在分区里记） |
| N3 | **不做**"不指定分区就能记账"的任何入口 | D8 |
| N4 | **不做**新建分区时预置任何分类 | D2 |
| N5 | **不改变**无运行时权限 / 纯离线 / 本地优先的产品边界；**不引入**账号、云同步、联网分析 | 产品定位 |
| N6 | **不改变**金额精度口径（以「分」为单位存储）、时间管理（可改过去任意时间）、贴图能力、隐私开关语义 | 既有已验收能力，本次为"保留不动" |
| N7 | **不新增**跨分区批量搬账、分类合并去重等高级管理 | 本次是骨架级重构，非功能膨胀 |
| N8 | **不做**分类在「全局 ↔ 某分区」之间迁移归属（暂列 P2 / 见 Q-11） | 决议未覆盖，需先确认 |

## 3. 用户故事

| # | 作为…… | 我希望…… | 以便…… |
|---|---|---|---|
| US-1 | 装修业主 | 打开 App 直接看到「装修」这张卡片和它的 26 万进度条 | 一眼知道钱烧到哪了，不用点进统计页找 |
| US-2 | 装修业主 | 点进「装修」分区，之后的每一笔都自动记在装修里 | 买建材时不用每次重选分区，也不会手滑记错桶 |
| US-3 | 装修业主 | 装修里只有「主材 / 人工 / 家具 / 家电」这些我自己的分类 | 26 万的去向能按环节拆开看，而不是一堆通用分类 |
| US-4 | 记账用户 | 日常开支里的「餐饮 / 交通」这类通用分类能一次定义、到处可用 | 不用在每个分区里重复建一遍同样的分类 |
| US-5 | 记账用户 | 能自己决定分类的先后顺序 | 把最常用的放在最顺手的位置，而不是被算法猜 |
| US-6 | 记账用户 | 在装修分区里也能记一笔装修退款/报销收入 | 收入不用跑到别的地方单独记 |
| US-7 | 记账用户 | 能随时在「明细」里跨分区看这个月的全部账、并搜索某一笔 | 有全局视角，也能一秒找回某笔具体账 |
| US-8 | 记账用户 | 删掉一个不用的分区时，系统告诉我里面的账和分类去了哪 | 不会莫名其妙丢数据 |
| US-9 | 装修业主 | 在平板/折叠屏上，分区详情也是舒服的双栏/宽屏体验 | 不因为这次改版回退我已有的多端体验 |

## 4. 需求池

> 优先级：**P0 = 必须**（不做则本次重构不成立）· **P1 = 应该**（体验完整性）· **P2 = 可选**（有余力再做）
> 每条均可验收：验收标准写的是**可观察的行为**，不写实现方式。

### 4.1 数据模型（分类归属）

| 编号 | 需求 | 优先级 | 验收标准 |
|---|---|---|---|
| FR-01 | 分类必须有一个**归属**：`全局` 或 `某一分区`。全局分类对全部分区可见；分区专属分类只在该分区可见 | **P0** | 同一分区内两种分类都能选到；切到另一个分区时，看不到上一个分区的专属分类 |
| FR-02 | 分区专属分类同样区分**支出 / 收入**类型（沿用既有 type 语义） | **P0** | 「装修」下可分别建有支出的「主材」与收入的「报销」；在表单切到"收入"时只出现「报销」等收入类分类 |
| FR-03 | 新建分区时**不预置任何分类** | **P0** | 新建「宠物」分区并进入，分类区为空态（见 EC-05），不出现任何分类 chips |
| FR-04 | 分类顺序由用户**手动**决定，无自动排序 | **P0** | 连续多次使用某分类后，其位置不变；只有用户上移/下移才改变顺序 |

### 4.2 导航与入口

| 编号 | 需求 | 优先级 | 验收标准 |
|---|---|---|---|
| FR-05 | 移除底部中央凸起「记一笔」按钮 | **P0** | 底部栏不再有凸起按钮；App 中不存在任何"不选分区即可记账"的全局入口 |
| FR-06 | 底部导航改为 **4 槽**：`分区 · 明细 · 统计 · 我的`（顺序即此） | **P0** | 手机底部栏 4 项，顺序与文案一致；大屏 Navigation Rail 同步为这 4 项 |
| FR-07 | **默认打开「分区」**（分区升为首屏） | **P0** | 冷启动 / 从最近任务返回后，落点都是分区首屏 |
| FR-08 | 记账必须从某个分区进入，不存在"无分区记账"路径 | **P0** | 遍历全部入口，均需先确定分区；明细页也不提供"直接新建"的独立入口（明细的新建走其所在分区的上下文，见 Q-06） |
| FR-09 | 收入记账**同样在分区内**完成，不单独开收入入口 | **P0** | 分区详情「记一笔」里可切到「收入」并保存成功，账目归属该分区 |

### 4.3 分区首屏

| 编号 | 需求 | 优先级 | 验收标准 |
|---|---|---|---|
| FR-10 | 分区首屏为**卡片列表**，每张卡片含：emoji + 分区名 + **本月花销** + **预算进度条** | **P0** | 四项信息均可读；见 FR-11/FR-12 口径 |
| FR-11 | 「本月花销」= 该分区**当前自然月**的**支出合计**（不含收入） | **P0** | 在某分区本月记一笔 100 元支出，卡片花销 +100；记一笔收入，卡片花销不变 |
| FR-12 | 预算进度条：`预算 > 0` 时显示进度；**超支（支出 > 预算）时变红**并给出超支额；`预算 = 0`（未设预算）时不显示进度条，只显示花销 | **P0** | 边界口径与现有统计页一致：支出**正好等于**预算不算超支；用量 ≥90% 视为接近上限 |
| FR-13 | 点击卡片进入该**分区详情** | **P0** | 进入后标题/上下文显示为该分区 |
| FR-14 | 分区首屏需有**新建分区**入口 | **P0** | 从首屏可完成"新建分区"（空态下尤其必须有，见 EC-04） |
| FR-15 | 金额显示尊重「隐藏金额」开关 | **P1** | 开关开启时，卡片花销显示为掩码而非真实数字（与明细/统计页一致） |

### 4.4 分区详情

| 编号 | 需求 | 优先级 | 验收标准 |
|---|---|---|---|
| FR-16 | 分区详情 = **账目列表** + 底部 **「记一笔」** 按钮 + 右上 **「管理」** | **P0** | 三要素齐全；「记一笔」在拇指可达区（底部），不遮挡列表 |
| FR-17 | 账目列表展示该分区的账目（支出与收入同列），收入用可区分的颜色/符号 | **P0** | 该分区的收入与支出都出现在列表里，视觉可区分 |
| FR-18 | 右上「管理」进入该分区的管理：管理**该分区专属分类** + **编辑该分区**（名称/emoji/备注/预算） | **P0** | 在管理里能增删改该分区专属分类，能编辑分区信息；不出现其他分区的专属分类 |
| FR-19 | 分区专属分类支持**手动排序**，排序入口在本管理页 | **P0** | 上移/下移生效并持久；记账表单里分类 chips 顺序随之改变 |
| FR-20 | 分区详情返回后回到分区首屏 | **P0** | 返回键 / 返回按钮回到首屏 |

### 4.5 记一笔表单（新流程）

| 编号 | 需求 | 优先级 | 验收标准 |
|---|---|---|---|
| FR-21 | 表单**不再出现"选择分区"这一行**；分区由进入路径确定 | **P0** | 表单内无分区 chips；不存在"能改成别的分区"的选择控件（编辑态见 EC-06） |
| FR-22 | 表单需**只读展示当前记账分区**（emoji + 分区名） | **P0** | 用户在保存前能明确看到"这笔记在装修"，且该展示不可点击改分区 |
| FR-23 | 分类候选 = **类型匹配的全局分类 + 类型匹配的当前分区专属分类** | **P0** | 切"支出/收入"时候选集合随之切换；专属分类只在本分区出现 |
| FR-24 | 全局分类与专属分类在界面上**可区分**（如分组小标题/来源标注） | **P0** | 用户能一眼看出哪些是"到处都有"的、哪些是"这个分区独有"的 |
| FR-25 | 表单保留并**不改变**：支出/收入切换、金额输入与校验、快捷金额、时间（可改过去）、备注、贴图（多张/放大/移除） | **P0** | 这些能力行为与改动前一致（回归验收） |
| FR-26 | 保存前必须有**有效金额**与**已选分类**；任一缺失时给出就地提示且不保存 | **P0** | 空金额/未选分类时保存被拦截并提示 |
| FR-27 | **取消分类的自动默认选中**（见 Q-01，若采纳） | **P0** | 打开表单时分类无预选；不选分类直接保存会被拦截 |

### 4.6 明细页 / 统计页的角色（同步更新）

| 编号 | 需求 | 优先级 | 验收标准 |
|---|---|---|---|
| FR-28 | 「明细」页角色明确为：**跨分区总览 + 搜索/筛选入口** | **P0** | 明细页仍能看到全部分区的账目（默认不限定分区），并保留搜索与筛选 |
| FR-29 | 明细页空态文案必须**同步更新**（不得再指向已移除的中央「＋」） | **P0** | 空态文案引导用户去分区记账，且给出可点击去向 |
| FR-30 | 明细页保留「分区筛选」，作为跨分区检索手段 | **P1** | 可按分区筛选；「全部分区」为默认 |
| FR-31 | 统计页的「分区预算」与分区首屏卡片的**信息重复**需处理（保留其一/精简其一/差异化） | **P1** | 同一信息不在两个页面以同一形态重复出现（见 Q-08） |

### 4.9 删除与数据安全（见第 6 节的完整边界表）

|---|---|---|---|

## 5. 关键流程

### 5.1 主路径：分区首屏 → 分区详情 → 记一笔 → 保存 → 返回

```
[冷启动]
   ↓
① 分区首屏（4 槽导航，默认 tab = 分区）
   · 卡片：🔨 装修 · 本月花销 ¥X · 进度条（超支变红）
   ↓ 点击卡片
② 分区详情：🔨 装修
   · 账目列表（支出/收入同列）
   · 底部「记一笔」        右上「管理」
   ↓ 点「记一笔」
③ 记一笔（分区已固定 = 装修，只读展示）
   分区：🔨 装修（不可改）
   支出 | 收入   ← 默认支出
   金额 → 快捷金额
   分类：本分区专属（主材/人工/家具/家电/设计费） + 全局分类（餐饮/交通/…）
   时间（可改过去） → 备注 → 贴图
   ↓ 点「保存」
④ 保存成功 → 返回 ② 分区详情
   · 提示「已记入 🔨 装修 · ¥XXX」并提供「撤销」
   · 列表刷新，卡片花销/进度条随之更新
   ↓ 返回键
⑤ 回到 ① 分区首屏（装修卡片花销已更新）
```

**验收要点**
- 全程**没有任何一次"选择分区"的动作**。
- ⑵ 的默认支出/收入为**支出**；⑶ 的分类候选**只包含**"本分区专属 + 全局"。
- ④ 的「撤销」在提示条窗口内可完整恢复该笔账（含贴图），沿用既有撤销语义。

## 6. 边界与例外

> 本节是本次重构**最容易遗漏**的部分，逐条给出行为定义与验收口径。

### EC-01 全局分类与专属分类在界面上如何区分、各自在哪管理

| 问题 | 结论 |
|---|---|
| 界面上如何区分 | 「记一笔」分类区**分组呈现**：先「本分区专属」（✅ 优先，贴近当前上下文），后「全局」。分组各带小标题或来源标注；视觉上可用不同容器色/边框区分。**同名不合并**（见 Q-02） |
| 全局分类在哪管理 | **不能**放在分区详情右上「管理」里（那是"该分区"的管理）。需要**新的稳定入口**（推荐：「我的」页 → 记账分组下新增「全局分类」）。**见 Q-03，必须定案**，否则全局分类无处可管 |
| 专属分类在哪管理 | 分区详情右上「管理」内，且只显示该分区的专属分类 |
| 排序 | 全局分类的排序在全局分类管理页；专属分类的排序在该分区的管理页。两组排序互相独立 |

**验收**：全局分类管理入口存在且可达；在该处新增的分类，进入**任意**分区都能选到。

### EC-02 删除分区时，其专属分类与账目怎么处理

| 处理对象 | 期望行为 |
|---|---|
| 账目 | **必须不丢失**。默认迁移到"排序最靠前的其余分区"（沿用既有口径），并在确认框中写明「该分区下的 N 笔账目将移入「X」」 |
| 专属分类 | **不得直接硬删**（可能有账目仍引用它，外键保护会失败——这是实现层事实，PM 层要求"结果必须正确且不报错"）。**推荐**：该分区的专属分类**降级保留为全局分类**（数据不丢，用户可再去全局分类管理里删），或随分区删除但**先把引用它的账目改到目标分区的兜底分类**。**见 Q-04，需架构师定案** |
| 确认框 | 必须同时说明**账目去向 + 分类去向**，不能只说其中一条 |

**验收**：删除一个有账目、有专属分类的分区后：无孤儿引用、无崩溃、无静默丢失；确认框文案与执行后的实际结果一致。

### EC-03 删除分类时，挂着该分类的账目怎么处理

| 场景 | 期望行为 |
|---|---|
| 删除**专属**分类（本分区内） | 引用它的账目改到 **同类型** 的兜底分类；兜底优先取"本分区其余同类型专属分类"，其次取"同类型全局分类"。确认框写明改到哪个分类 |
| 删除**全局**分类 | 引用它的账目可能**跨多个分区**。兜底建议取"同类型的其余全局分类"。需注意：这些账目所在分区**可能并不包含**兜底分类——**这不影响历史账目的显示**（见 EC-09），但会影响用户之后编辑这笔账时的可选范围 |
| 同类型分类**只剩一个** | 沿用既有口径：拒绝删除并给出可读原因（"至少保留一个分类"），但文案需适配新模型（区分全局/专属）。**见 Q-05** |
| 类型不同 | 支出分类的兜底不得落到收入分类上 |

**验收**：删除任一分类后，其账目均指向一个**同类型**的有效分类；无外键失败、无孤儿。

### EC-04 极端情况：分区被删光（0 个分区）

- 现状：`deleteSection` 在"只剩一个分区"时**拒绝删除**（`至少保留一个分区`）。
- 新模型下：因为「记账必须先进分区」（D8），若允许 **0 分区**，则 App 将**无处可记账**——但这也是**合法且必须能表达**的状态（用户刚清空一切）。
- **要求**：
  1. 分区首屏在 0 分区时显示**空态**：一句说明 + **显著的新建分区入口**；不得白屏、不得崩溃。
  2. 「明细」页此时仍可用（历史账目为空，显示空态），统计页显示空态。
  3. 是否允许删到 0，需要在 Q-06 定案；**无论哪种定案，都必须有明确的空态与引导**。

**验收**：构造 0 分区状态，App 全部 tab 均可打开且不崩溃，分区首屏给出新建引导。

### EC-05 某分区一个分类都没有时，记一笔界面长什么样

- 触发：新建分区（FR-03 不预置分类）后直接记账。
- **要求**：
  1. 分类区显示**空态**：「这个分区还没有分类」+ **「＋ 新建分类」**（就地创建，无需离开表单；若跨页创建，返回后候选需自动刷新）。
  2. 就地新建时，**类型默认跟随当前表单的支出/收入**，并默认归属**当前分区**。
  3. 在无分类状态下点「保存」，必须被拦截并提示（不得发出无分类的账目）。
  4. 若全局分类存在而本分区没有专属分类：**不显示空态**，正常显示全局分类（只是没有"本分区专属"分组）。

**验收**：新建分区 → 直接记一笔，能在表单内完成"建分类 → 选分类 → 保存"闭环。

### EC-06 编辑已有账目时能否改分区（把账目移到别的分区）

- 现状：表单里有分区 chips，可随时切换分区——这正是用户不满 1 的来源。
- **推荐方案（需 Q-07 定案）**：**编辑态也不在表单内改分区**，分区只读展示；"把这笔挪到别的分区"走**明细页既有能力**（长按账目 → 移动到分区）。
- 若采纳推荐方案：
  - 编辑表单的分区行同样为只读。
  - 若账目的**当前分类**在其所属分区里"不可见"（例如全局分类已被删除、或分类归属变了），编辑时必须能**正常显示并保留**该分类，同时允许用户改成新的可见分类（见 EC-09）。
- 若最终决定**允许**表单内改分区（备选）：切分区后必须处理"原分类在新分区不可见"——需清空分类选择并要求重选，且在确认时提示"分区已变，请重选分类"。

**验收**：无论哪种定案，编辑一笔老账并保存后，账目的分区与分类始终一致、合法，不出现"分区=装修、分类=只在旅行可见的分类"这类非法组合。

### EC-07 「保存并再记」在新流程下的行为

- 现状：保留 类型 / 分类 / 分区 / 时间，清空 金额 / 备注 / 贴图，光标回金额。
- 新流程下的**矛盾点**：分区已固定，无歧义；但**分类是否保留**存在两种取向：
  - 保留分类 → 连续记同一类（如连续多笔"主材"）最快；
  - 清空分类 → 避免"手一滑把下一笔也记成上一笔的分类"。
- **推荐**：保留**分区 + 类型 + 时间**，**清空分类选择**（回到"必须选分类"态），并在提示条里显示「已记入 🔨 装修 · ¥XXX」，让用户明确刚落了一笔。理由：本次主线目标是"记对桶（分区）"，分区已由上下文保证；分类是第二决策点，清空可避免串联误记。
- **必须**：提示条仍显示"分区 + 金额"（沿用现有格式），隐私模式下金额显示为「金额已隐藏」。

**验收**：点「保存并再记」后：分区不变、类型不变、金额清空、分类回到未选中、表单不退出、提示条显示"分区 + 金额"。

### EC-08 旧账目 / 旧分类的兼容

- 用户**尚未真正投入使用**（D13），库内为测试数据，**无需保守迁移**。
- **要求**：
  1. 重建后的示例数据（FR-32~35）中，每条账目的 `分类` 必须与所在 `分区` **语义自洽**（不要把"主材"这种装修专属分类挂在"旅行"上）。
  2. 若实现上采用"改归属 + 补分类"的渐进策略（D14），则需保证：升级后**不出现**"账目引用了已不存在或不可见的分类"的脏态；即便出现，App 也必须能**正常显示与编辑**（不得崩溃、不得空白）。
  3. 旧分类若与新模型语义冲突（如全局的"购物"被同时用作装修使用），重建时应**归位到合理归属**，而不是原样保留造成歧义。
- **明确不要求**：保留测试数据的原貌；不要求用户手动处理任何数据。

**验收**：升级安装后，全部账目均可正常打开、编辑、保存；分类占比/统计结果与账目一致；无崩溃。

### EC-09 历史账目引用"当前分区不可见"的分类

- 场景：某账目引用分类 C，但 C 后来被删除/归属改变，导致在"当前分区 + 当前类型"下 C 不属于候选集合。
- **要求**：
  1. 该账目**照常显示**其真实分类名与 emoji（列表、详情、统计、导出均不受"可见性"规则影响）。
  2. 编辑该账目时，表单**必须能展示当前分类**（以"不在候选列表中"的形式呈现，如单独一个标记为"历史分类"的 chip 或只读标签），且**不得在用户未改动的情况下静默替换**它。
  3. 用户主动选择一个新分类后保存，视为一次显式的替换。

**验收**：构造"账目引用了非候选分类"的场景，列表与编辑均正确、不丢失、不静默改写。

### EC-10 「明细」页在新结构中的角色

| 维度 | 定位 |
|---|---|
| 是什么 | **跨分区总览**：默认「全部分区」，按月查看全部账目（按天分组 + 每日小计 + 三格概览） |
| 入口价值 | **搜索入口**（关键词，跨全部时间）+ **筛选入口**（类型 / 分类 / 分区） |
| 不承担 | 不再是「记一笔」的主入口（中央 ＋ 已移除）；不做"直接新建"的独立按钮 |
| 空态 | 文案改为引导去「分区」记账（FR-29），例如"本月还没有账目，去「分区」里挑一个开始记"，并提供可点的去向 |
| 账目操作 | 长按账目仍提供：复制、**移动到分区**、删除+撤销（这些能力在新模型下价值上升，是跨分区调整的主管道） |

**验收**：明细页可查看全部分区账目、可搜索、可筛选、空态文案不再提及已移除的按钮。

| **Q-07** | **编辑已有账目时能否改分区？** 决议只说"记账必须先进分区"，未覆盖编辑态 | 若表单仍保留可切换的分区，则不满 1 会**在编辑态复发**；若不允许，需明确"跨区移动"走哪条路 | **推荐：编辑态分区只读**，跨区移动统一走**明细页长按账目 → 「移动到分区」**（该能力已存在）。这样"分区是上下文"的心智模型全程一致，且表单更短。**需要用户确认**是否接受"不能在编辑页改分区" |
| **Q-08** | **分区预算进度在"分区首屏"和"统计页"重复** | 同一信息两个页面同形态出现，与"减少阅读压力"相悖；也让用户不确定该看哪个 | 建议：**分区首屏=行动视角**（这个桶还剩多少，超支先红）；**统计页=分析视角**（趋势 / 占比 / 每日支出）。若保留统计页的分区预算块，应**明确差异化**（如统计页只列"接近上限/超支"的分区做预警）。**请用户裁量是否从统计页移除分区预算块** |
| **Q-09** | **统计页「分类占比」在有多个同名专属分类时如何聚合？** | 若按**名称**聚合，会把"装修·材料"和"宠物·材料"合并（大概不是用户想要的）；若按 **id** 聚合，则出现两行同名"材料"，用户看不懂 | 建议**按分类 id 聚合**，并在标签上带**分区名消歧**（如「🔨 装修 · 材料」）。需要确认 |
| **Q-10** | **分区首屏是否有月份切换？** D10 说的是"本月花销" | 若只有"本月"，用户看不到上月对比；若可切月，首屏又变复杂（与目标 G3 冲突） | 建议**固定为当前自然月，不做切换**（保持首屏极简）；月度对比交给统计页。需要确认 |
| **Q-11** | **是否允许修改分类的归属**（全局 ↔ 某分区）？ | 决议只定义了"新建时可选归属"，未定义"之后能否改"。用户在把"购物"错建成全局后，只能删了重建 | 建议**本次不做**（N8，P2）；删除 + 重建可满足需求，避免引入"改归属后账目可见性变化"的连锁复杂度。若用户希望有，再单独立项 |
| **Q-12** | **分区详情账目列表的组织形态**：按天分组（同明细页）还是简单倒序列表？ | 影响"减少阅读压力"的达成度与实现量 | 建议**按天分组、与明细页一致**（复用既有组件心智、每日小计对装修业主有用）；若为极简可先做"时间倒序平铺"。需要确认 |
| **Q-13** | **明细页是否保留"新建记账"的快捷路径？** 中央 ＋ 已移除，但明细页是用户看账最久的地方 | D5/D8 只说移除中央按钮、必须先进分区。若明细页完全没有新建入口，用户在"看到一笔想补记"时会觉得别扭 | 建议：明细页**不提供独立新建按钮**（严格符合 D8）。若用户强烈需要，退路是"点某笔账 → 复制"或"分区筛选到某个分区 → 就地记一笔"。**需要确认** |
| **Q-14** | **分区是否也需要手动排序？** D3/D4 只覆盖了"分类手动排序" | 分区数量会增长，顺序影响首屏"第一眼看到哪个桶"（对装修用户，装修应排第一） | 建议**分区也支持手动排序**，入口放在分区首屏（如长按拖拽或管理态上下移）。若不做，则需明确分区顺序规则（如按创建时间）。**需要确认** |
| **Q-15** | **术语统一**：产品面向用户的文案该用「分区」还是别的词？"分区"对普通用户偏技术化 | 术语影响全 App 文案与用户理解成本（"桶"？"账本"？"分类"与"分区"在中文里也易混） | 建议**沿用「分区」**（已在六轮迭代中作为既有术语，README/设计稿/截图统一），降低改版噪音。若用户希望更口语化（如"账本"），需**一次性全局替换**（含文案、空态、确认框、导出表头）。**需要确认** |

## 9. 验收总纲（可交付测试直接消费）

1. **无分区不记账**：全 App 遍历，无任何"未选分区即可保存账目"的路径。
2. **分类归属正确**：任一分区下，分类候选严格 = 同类型全局分类 + 同类型本分区专属分类；切换分区后专属分类集合随之变化。
3. **分区桶正确**：在「装修」记的每一笔，其归属分区都是「装修」，且用户无需在表单内做任何分区选择。
4. **预算可视**：分区卡片显示本月支出与预算进度；超支变红；未设预算不显示进度条。
5. **零分类可用**：新建分区（无任何分类）能走通"表单内建分类 → 选中 → 保存"闭环。
6. **删除无损**：删除分区 / 分类后，账目与分类均指向合法目标，无孤儿、无崩溃、无静默丢失，且确认框说明了后果。
7. **兼容正确**：升级后所有账目可正常查看 / 编辑 / 统计 / 导出。
8. **多端与无障碍不回归**：三种窗口 + 2.0× 字号下主要流程可达、不裁切。
9. **既有能力不回归**：金额校验、快捷金额、时间可改、备注、多张贴图与放大、撤销、隐藏金额、应用锁、导出/备份恢复。

### 10.2 用户裁定（3 项）

| # | 裁定 | 实现含义（架构师须按此设计） |
|---|---|---|
