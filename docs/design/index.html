设计定位与假设

在动笔之前，先明确这次重构要解决的问题，以及本方案基于哪些假设。假设部分请重点确认—— 它们决定了信息架构与功能取舍。

设计读数（Design Read）

交付物移动应用界面系统 + 关键屏高保真稿 + 线框 + 规范
核心用户装修期家庭决策者（30–40 岁）与日常记账习惯者（22–35 岁）
视觉语言温和人文派：暖中性 + 青绿品牌色 + 等宽数字 + 大圆角
改造模式Overhaul 全量重构 保留底层数据与功能，重做视觉与信息架构

五个设计刻度（1–10）

视觉张力5 · 有性格但不喧哗
动效强度4 · 只做有意义的过渡
信息密度6 · 一屏 5–7 条账目
素材依赖2 · 无外部品牌素材，纯界面
品牌保真6 · 保留青绿资产，重塑细节

六条设计原则

1 · 一笔记账 ≤ 3 次点击

默认值足够聪明：类型、时间、分区都预填合理值，用户只需要输入金额。

2 · 数字是主角

金额使用等宽数字与大字号，视觉权重最高；装饰性元素一律让位。

3 · 分区即项目

分区承载用途与预算，是「简账」区别于普通记账工具的差异化核心。

4 · 状态永远透明

本地优先意味着没有网络等待——但保存、迁移、删除都要有明确反馈与撤销。

5 · 克制的色彩

只有支出、收入、预警三种语义色，其余全部交给暖中性色阶。

6 · 拇指优先

高频操作固定在屏幕下三分之一，单手可达；主操作永不藏在菜单里。

01

目标用户与使用场景

记账是高频、碎片、低耐心的操作。设计的所有取舍，都围绕「用户在什么状态下打开这个 App」展开。

三类典型用户

装
装修当家的人
34 岁 · 主力用户 · 占比约 45%

房子正在装修，三个月要花掉二十几万，涉及十几个供应商。最怕的不是花钱，而是花到哪一步了说不清。

分区分项记账预算进度大额支出留痕票据贴图

试过好几款记账软件，都因为记账太麻烦放弃。需求很简单：三秒记一笔，月底能看一眼钱去哪了。

五个真实场景

场景当时的状态设计对策
地铁上记一笔单手、站着、注意力碎片化主操作固定在屏幕下缘；数字键盘与「记一笔」页面拇指可达；取消操作不会丢失已填内容
建材市场当场付款光线差、手上有灰、赶时间高对比大字号；金额输入用超大数字；分类用 emoji + 文字双编码，弱光下依然可辨；一屏内完成保存
月底沙发上复盘放松、愿意花 10 分钟统计页按「总览 → 结构 → 趋势 → 项目」叙事排列；点击任意图表可下钻到对应明细
晚上补记昨天的账记忆尚存、怕记错日期时间字段提供「今天 / 昨天 / 前天」快捷选项，默认「今天」；改日期只需一次点击
换新手机担心数据丢失「我的」页第一屏即展示「数据保存在本机」+ 一键导出 CSV / 完整备份，并说明系统云备份已开启

痛点 → 设计对策

痛点：记账步骤多，坚持不下来

→ 「记一笔」全屏页只问四件事：金额、分类、备注、贴图——分区由进入路径携带、表单内只读；金额输入即出键盘，无二次跳转。

痛点：大额支出记了，但看不出项目进度

→ 分区字段化预算，「分区」首屏每个分区一条预算进度条，超支转琥珀色并给出文字说明。

痛点：统计图好看但不知道点进去看什么

→ 所有图表可点击下钻：点某个分类扇区 → 跳到明细页并自动带上该分类筛选，形成闭环。

痛点：怕数据丢了，又不想注册账号

→ 「我的」页用一句话说明本地存储 + 系统云备份状态，把「导出」做成显性按钮而非藏在三级菜单。

02

信息架构与导航结构

记账类产品的信息架构有一个天然主轴：分区（怎么归类）→ 流水（发生过什么）→ 汇总（意味着什么）。 「分区优先」重构后，分区升为首屏（默认落点），一级导航收敛为 4 槽（分区 · 明细 · 统计 · 我的）； 「记一笔」不再是全局主操作，统一从「分区详情底部」或「明细页先选分区」进入。

支出 / 收入金额分类（专属 / 全局分组） 分区（只读）日期时间备注贴图
为什么这样组织？
层级原则一级导航只放不同性质的任务；同一任务的不同维度用页面内 Tab（如「分区 / 分类」）
深度原则任何功能不超过 2 层。原方案里「分区管理」藏在第三个 Tab 的二级 Tab 中，认知成本过高
主次原则记账必须携带分区上下文，「记一笔」不再占据全局槽位；入口收敛到「分区详情底部」与「明细页先选分区」，避免「记了账却没地方归」
闭环原则统计页每个图表都能下钻回明细并自动带上筛选条件，避免「看得到、点不进」
导航槽位对比

原方案：3 个 Tab（明细 / 统计 / 管理）+ 右下 FAB
「分区优先」重构：4 槽位（分区 · 明细 · 统计 · 我的），分区升首屏，移除中央凸起「记一笔」
依据：分区承载用途与预算，是「简账」的差异化核心；「记一笔」需分区上下文，故从全局槽位退场，改由分区入口承载。

04

控件与组件样式

组件是设计系统的执行单元。以下 16 组组件均给出尺寸、状态与无障碍要求三要素—— 状态覆盖完整的组件，才能避免开发阶段「照着静态稿猜交互」。

按钮 Button6 种层级 · 3 种尺寸
层级用法：一屏内最多一个 Filled 按钮（主操作）；Tonal 用于次级强调；Outlined / Text 用于退出类操作；Danger 仅用于不可逆动作且必须配合二次确认。
尺寸：高度 44 / 52dp，圆角 14dp，左右内边距 20dp；触控热区不小于 48×48dp（小尺寸按钮通过外层 padding 补足）。
状态：hover 提升 1dp 并加深底色（大屏）· pressed 底色降至 brand-700 · disabled 透明度 38% 且不可聚焦 · loading 时按钮内文字替换为 16dp 转圈并锁宽防止跳动。
输入框 Text Field默认 / 聚焦 / 错误 / 禁用
分区名称不能为空
用法：输入框采用「填充式」而非描边式——暖底色上的浅填充更柔和，也更容易在浅色卡片上形成温柔的分区。
校验：错误态用红色 1.5dp 描边 + 6% 红色底 + 下方 11.5px 提示语，并在输入框下方而非顶部提示，避免用户视线跳回；错误修正后立即恢复默认态。
无障碍：标签与输入框用 for/id 关联；错误提示使用 aria-live="polite"，读屏会在停止输入后播报。
金额输入 Amount Field核心组件
¥ 1,280
光标常驻 · 千分位实时分组 · 输入即校验
快捷金额（可配置）

关键交互流程与状态反馈

记账产品的核心体验不在「好看」，而在每一次操作之后用户是否确信事情已经发生。 以下流程定义了三件事：几步完成、每步看到什么、异常时怎么办。

主流程 · 记一笔（明细页入口先选分区）

① 唤起

从「分区详情」底部「记一笔」，或在「明细」页点「＋ 记一笔」后先在分区选择器中选定分区（不可跳过）。全屏页推入，输入法与数字键盘自动升起。

→
② 输金额

默认「支出」、当前时间；分区为上下文、记账时只读（表单内不存在改分区的控件）。只需按数字。

→
③ 选分类

按「本分区专属 / 全局」分组呈现；不预选、不自动前置——首次进入需主动选择，避免误记。

→
④ 保存

底部 52dp 主按钮；成功后返回来源页并提示「已记入 …」+ 撤销。

步骤即时反馈（< 100ms）结果反馈（提交后）异常处理
输入金额数字即时千分位分组，光标常驻，非法字符直接被过滤—金额为空或为 0 → 保存按钮保持禁用并显示原因
选择分类chip 150ms 底色与文字色过渡，气泡轻微放大 1.03×—无分类时给出「先创建一个分类」的直达入口
添加贴图立即出现加载占位，读取成功替换为缩略图保存时写入本地目录并出现 📷 计数图片读取失败 → 提示「有 N 张图片读取失败，请换一张」，账目仍可保存
点击保存按钮进入 loading 并锁定宽度（防止跳动）回到来源页 + Snackbar「已记入 🔨 装修 · ¥2,000.00」+ 撤销写库失败 → 返回表单并保留全部输入，提示「保存失败，请重试」

分支流程

编辑账目

列表项点击 → 同一表单（标题变「编辑账目」，右上角出现删除）→ 保存后 Snackbar「已更新」+ 撤销。
贴图默认全部保留，用户主动移除才删除文件。

删除账目

长按列表项 → 快捷菜单「删除」→ 不弹确认框，直接删除并给 4 秒撤销。
理由：可撤销的删除比二次确认更快，也不会让人误以为已经删掉了。

删除分区

必须二次确认，且提示中写明受影响笔数与迁移目标分区。
分区删除会批量改变数据归属，属于「不可用 4 秒撤销解决」的高风险操作。

分类网格列数 4 → 6 → 8，卡片高度不变（保持触控目标尺寸一致）
环形图 + 图例Compact 纵向堆叠 → Medium 起横向并排，图例获得更宽的文字空间
筛选 chipsCompact 横向滚动 → 大屏自动换行全部展示，减少滚动
对话框Compact 底部升起 → 大屏居中固定宽度（560dp）
金额输入字号保持 44px 不变（金额永远是主角），仅增加可用宽度
折叠屏特别处理

铰链分割时（FoldingFeature 为 HALF_OPENED）：
· 内容不得跨过铰链区域，列表与详情分列两侧
· 桌面模式（半折立在桌上）时，上半屏放内容、下半屏放操作区
· 展开 / 折叠切换时保持滚动位置与已填表单，绝不重置页面

大屏的三个「利用」而非「放大」

① 利用宽度减少跳转：列表点选即在右侧展开详情，不推入新页面；
② 利用高度同屏对比：统计页把「结构（环图）」与「趋势（柱状）」并排，便于对照；
③ 利用指针精度：大屏启用 hover 态与右键菜单（复制账目、移动到其它分区）。

9.2 设计准则

触控与操作
  • 触控目标 ≥ 48×48dp，相邻目标间距 ≥ 8dp
  • 列表项整行可点，不要求精确点中图标
  • 破坏性操作永不与常用操作相邻
  • 所有手势操作都有等价的按钮入口
色彩之外的第二编码
  • 支出用 −、收入用 +，符号先于颜色
  • 选中态同时使用底色 + 字重 + （必要时）对勾
  • 预警不只靠琥珀色，必须配「已超支 ¥180」文字
  • 图表扇区配图例文字与百分比，不依赖颜色记忆
读屏与语义
  • 金额朗读为「支出两千元整」，而非「减 ¥2,000.00」
  • emoji 分类图标必须提供文字标签，避免读屏念出图形名称
  • 图表提供「本月支出 2,212.30 元，其中居住占 90%」的文本摘要
  • 列表项合并为一条语义节点，横滑不产生多个焦点

9.3 一致性：Do / Don't

✕ Don't 用纯红 #DC2626 大色块铺满支出卡 —— 记账场景下会制造「钱出问题了」的焦虑；
统计页用 8 种高饱和色各占一块 —— 视觉噪音掩盖数据本身；
不同页面的卡片圆角、内边距随性变化 —— 用户说不出哪里不对，但会觉得「不精致」。
✓ Do 支出只用暖红标注数字与图标，大面积交给中性色 —— 冷静、克制、可长时间停留；
图表用同明度、等色相差的色板，并配图例文字 —— 颜色只做辅助识别；
圆角与间距全部来自 tokens，任何新组件先找现有令牌 —— 一致性来自约束，而非自律。
